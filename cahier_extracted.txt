CAHIER DES CHARGES COMPLET — SÛRCHECK AI
MVP de prévention et d’analyse des risques d’arnaques numériquesBénin → Afrique francophoneDurée cible : 14 jours
1. VISION DU PRODUIT
SûrCheck AI est une plateforme web mobile-first permettant aux utilisateurs d’analyser rapidement un message, un SMS ou un lien potentiellement frauduleux avant d’envoyer de l’argent ou de partager des informations sensibles.
Promesse principale :« Avant d’envoyer ton argent, vérifie. »
Le produit ne doit jamais affirmer automatiquement qu’une personne est criminelle. Il doit présenter un niveau de risque, les signaux détectés et des recommandations de sécurité.
2. PROBLÈME
Les utilisateurs reçoivent régulièrement des faux messages Mobile Money, de fausses offres d’emploi, de faux concours, de faux cadeaux, de faux investissements, des messages WhatsApp suspects et des liens de phishing.
Avant une transaction, beaucoup se demandent :« Est-ce que je peux faire confiance à ça ? »
Le MVP doit apporter une réponse simple, rapide et compréhensible.
3. OBJECTIF DU MVP
Permettre à un utilisateur de :1. Coller un message suspect.2. Coller un lien suspect.3. Recevoir un score de risque de 0 à 100.4. Comprendre les signaux détectés.5. Signaler un numéro, un lien ou un message.6. Consulter son historique.7. Tester le produit gratuitement avant toute monétisation.
Le MVP ne cherche pas à détecter parfaitement toutes les arnaques du monde. Son objectif est de valider l’intérêt réel des utilisateurs.
4. UTILISATEURS CIBLES
Marché initial : Bénin.Cibles prioritaires :- Étudiants.- Travailleurs.- Commerçants.- Utilisateurs Mobile Money.- Chercheurs d’emploi.- Utilisateurs WhatsApp et Facebook.
Expansion progressive :1. Bénin.2. Togo.3. Côte d’Ivoire.4. Sénégal.5. Burkina Faso.
Le produit doit progressivement intégrer les réalités et scénarios locaux.
5. FONCTIONNALITÉS MVP
A. Analyse de texteL’utilisateur colle un message suspect.Résultat :- Niveau : Faible / Prudence / Élevé.- Score de risque.- Signaux détectés.- Catégorie probable.- Conseils de sécurité.
B. Analyse de lienLe système :- valide l’URL ;- vérifie la base interne ;- consulte des sources de réputation/phishing compatibles avec l’usage ;- retourne un niveau de risque.
C. Signalement communautaireL’utilisateur peut signaler :- un numéro ;- un lien ;- un message ;- une page.
Catégories :- Mobile Money ;- faux emploi ;- faux investissement ;- phishing ;- faux cadeau ;- usurpation ;- autre.
D. Historique utilisateur.E. Interface d’administration minimale pour modérer les signalements.
6. RÈGLES JURIDIQUES ET DE SÉCURITÉ
Ne jamais publier automatiquement qu’un individu est « un escroc ».
Utiliser plutôt :- « Risque potentiel détecté »- « Plusieurs signaux nécessitent une vérification »- « Signalement communautaire non confirmé »- « Vérifiez avant toute transaction »
Les signalements doivent être modérés.Prévoir consentement, politique de confidentialité, limitation des données collectées et anonymisation lorsque des données sont utilisées pour améliorer le système.

Utilisateur→ Application Next.js→ API / moteur d’analyse→ Règles + modèle ML + vérification URL→ PostgreSQL
Stack :- Frontend : Next.js + TypeScript + Tailwind CSS.- Backend IA : Python + FastAPI.- Machine Learning : scikit-learn.- Traitement données : pandas.- Base : PostgreSQL.- Déploiement MVP : Vercel pour Next.js et API compatible.- Paiement futur : FedaPay.- Détection URL : PhishTank/OpenPhish ou autres sources compatibles après vérification des conditions d’utilisation.

9. MOTEUR D’ANALYSE
Niveau 1 : règles locales à coût nul.Exemples :- Demande de code secret : +50.- Demande d’argent : +25.- Urgence artificielle : +15.- Promesse de gain : +25.- Lien suspect : +30.
Niveau 2 : modèle ML.Classificateur initial possible :- Logistic Regression.- Naive Bayes.- Linear SVM.
Sortie :- classification ;- confiance ;- catégorie probable.
Niveau 3 : vérification externe des URLs.
Les modèles coûteux de type LLM ne doivent être utilisés qu’ultérieurement pour les cas ambigus.

Analyse un message ou une offre et identifie les signaux potentiellement associés à une tentative de fraude.

Analyse notamment :1. Demande d’argent.2. Pression psychologique.3. Urgence artificielle.4. Demande de code ou d’information sensible.5. Promesse de gain irréaliste.6. Usurpation possible.7. Lien ou contact suspect.
Retourne :- niveau de risque ;- score entre 0 et 100 ;- signaux détectés ;- catégorie probable ;- recommandations de sécurité.

COMPLÉMENTS STRATÉGIQUES ET TECHNIQUES — SÛRCHECK AI
Cette partie complète le cahier des charges existant sans répéter ses sections. Elle formalise les décisions et orientations déjà définies pour transformer le MVP en produit réellement testable, monétisable et extensible.
21. POSITIONNEMENT ET PROMESSE
SûrCheck est un outil d’aide à la décision, pas un « détecteur d’escrocs ». Il transforme une situation douteuse en niveau de risque, preuves/signaux compréhensibles et actions concrètes.
Promesse prioritaire à tester : « Vérifie avant d’envoyer ton argent. » Variante : « Envoie le message avant d’envoyer l’argent. »
Moment de valeur : juste avant un paiement ou avant de partager un code, une information sensible ou un document.
Le produit doit répondre dans cet ordre : Quel est le risque ? Pourquoi ? Que dois-je faire maintenant ?
Ne jamais afficher « 100 % sûr ». Pour un résultat rassurant, utiliser plutôt « Aucun signal majeur détecté dans les éléments analysés ».
22. PARCOURS UTILISATEUR
Le premier contact doit être sans friction : landing → saisie/import → analyse → résultat. L’inscription ne doit pas bloquer la première valeur lorsque cela n’est pas nécessaire.
Résultat gratuit : niveau + score + quelques signaux prioritaires. Rapport approfondi : détails supplémentaires, vérifications disponibles et recommandations avancées.
Paiement : création du checkout → paiement → confirmation serveur par webhook → crédit/déblocage → historique.
Actions principales après résultat : « Vérifier un autre contenu », « Signaler », « Partager » et, lorsque disponible, « Obtenir l’analyse détaillée ».
23. MOTEUR DE DÉCISION HYBRIDE
Le score ne doit jamais dépendre uniquement d’un LLM. Il combine règles déterministes, modèle ML, intelligence de réputation des URLs et signaux communautaires modérés.
Pipeline : normalisation → extraction → règles → ML → réputation → agrégation → calibration → explication.
Signaux prioritaires : demande de PIN/OTP/code, demande d’argent, urgence artificielle, menace, gain irréaliste, paiement préalable, usurpation, changement inhabituel de canal, URL incohérente ou raccourcie, demande d’informations sensibles.
Chaque résultat doit conserver les facteurs ayant contribué au score et la version du moteur utilisée.
Prévoir une notion de confiance/incertitude : lorsque les éléments sont insuffisants, le système doit le dire plutôt que forcer une conclusion.
24. SCÉNARIOS LOCAUX À COUVRIR
Faux agent Mobile Money, faux service client, faux vendeur en ligne, faux recrutement, faux concours/cadeau, faux investissement, usurpation d’un proche, faux paiement/reçu, fausse livraison, faux remboursement, phishing de compte, faux support technique et demandes de codes.
Pour chaque scénario : exemples anonymisés, expressions locales, signaux forts/faibles, règles, contre-exemples légitimes et cas limites.
Conserver une bibliothèque par pays afin que le vocabulaire et les pratiques puissent évoluer sans modifier toute l’application.
25. ANALYSE D’IMAGE / OCR
Permettre l’import d’une capture de SMS, WhatsApp, publication, annonce, page de paiement ou reçu.
Pipeline : image → OCR → nettoyage → extraction des URLs/numéros → moteur de risque → résultat.
Gérer les captures compressées, texte partiellement lisible, caractères spéciaux et mélange français/anglais.
Les images doivent être conservées le moins longtemps possible et seulement selon une politique de conservation explicite.
26. RÉPUTATION DES NUMÉROS
Après le cœur texte/image, ajouter une recherche de numéro basée sur les signalements modérés, leur récence, fréquence, catégorie et qualité.
Afficher « Des signalements ont été reçus concernant ce numéro » plutôt que « ce numéro appartient à un escroc ».
Normaliser les numéros par pays et utiliser autant que possible une empreinte/hachage afin de limiter l’exposition du numéro brut.
27. BASE DE CONNAISSANCES — ACTIF STRATÉGIQUE
L’avantage défendable de SûrCheck doit devenir sa base de connaissances sur les méthodes d’arnaque en Afrique francophone, et pas seulement son interface ou son modèle IA.
Boucle d’amélioration : analyse → feedback → signalement → modération → enrichissement des patterns/règles → nouvelle analyse.
Stocker les scénarios, pays, canaux, signaux, domaines, moyens de paiement, statut de vérification et résultats des validations.
Un grand nombre de signalements augmente un signal de réputation mais ne constitue pas automatiquement une preuve.
28. MODÉRATION ET CONTESTATION
Workflow : nouveau signalement → détection des doublons → examen des éléments → classement → décision → journalisation.
Statuts : nouveau, en vérification, confirmé par éléments suffisants, non confirmé, contesté, retiré.
Conserver les preuves privées et publier uniquement les informations nécessaires à l’évaluation du risque.
Prévoir un mécanisme de contestation/correction et des logs d’administration.
29. MONÉTISATION À TESTER
Le modèle prioritaire devient : valeur gratuite immédiate → paiement pour approfondir. Les prix doivent être expérimentés, pas considérés comme définitifs.
Tests possibles : analyse simple 100–200 FCFA ; rapport détaillé 300 FCFA ; formule renforcée 500 FCFA.
Les packs peuvent être structurés autour de 5, 20 et 50 analyses. Tester également l’achat d’une seule analyse premium pour réduire la friction.
L’abonnement mensuel ne doit être introduit qu’après observation d’un usage récurrent. Il peut ensuite inclure un quota d’analyses, historique avancé et alertes.
Objectif économique du MVP : obtenir des paiements réels au moment où l’utilisateur ressent un risque, avant d’optimiser le revenu récurrent.
30. PAIEMENT ET INTÉGRITÉ DES TRANSACTIONS
Le navigateur ne doit jamais décider qu’un paiement est réussi. La source de vérité est la confirmation serveur du prestataire.
Utiliser un identifiant de transaction unique et un traitement idempotent afin d’éviter les doubles crédits.
Ne jamais exposer les clés secrètes dans le frontend. Utiliser des variables d’environnement côté serveur.
FedaPay peut servir pour tester les paiements locaux ; Chariow peut être évalué pour des produits numériques et son checkout. Vérifier avant production les fonctionnalités, frais, limites et conditions actuelles.
31. ARCHITECTURE DE PRODUCTION
Frontend : Next.js + TypeScript + Tailwind CSS.
API : FastAPI/Python avec endpoints versionnés.
Base : PostgreSQL ; stockage objet temporaire pour les images.
Services logiques : analyse, OCR, intelligence URL, scoring, réputation, paiement, notifications et administration.
Déployer initialement sur Vercel si les contraintes d’exécution sont compatibles, tout en gardant l’architecture suffisamment découplée pour déplacer les traitements lourds plus tard.
Ajouter logs structurés, suivi des erreurs, temps d’analyse, coût par analyse, webhooks et disponibilité.

34. SÉCURITÉ ET CONFIDENTIALITÉ
Rate limiting par IP/compte, anti-spam des signalements et quotas d’analyse.
Ne pas ouvrir directement des URLs arbitraires depuis le serveur applicatif. Utiliser des services de réputation ou un environnement isolé.
Valider taille/type des fichiers, empêcher les uploads exécutables et protéger les secrets.
Minimiser les données personnelles et prévoir politique de confidentialité, durée de conservation, suppression et conditions d’utilisation.
Les captures/conversations privées ne doivent pas servir à entraîner le système sans base légale et consentement approprié.
Afficher clairement que SûrCheck fournit une évaluation de risque et non une garantie.
35. QUALITÉ DU MODÈLE
Construire un jeu de validation indépendant avec messages légitimes et frauduleux provenant de plusieurs catégories.
Mesurer précision, rappel, F1, matrice de confusion, faux positifs, faux négatifs et calibration.
Tester particulièrement les erreurs dangereuses : faux négatif sur une demande de code, phishing, faux emploi ou faux paiement ; faux positif sur un commerce légitime.
Utiliser les retours humains pour améliorer règles, données et interface.
Prévoir une sortie « incertain » pour les cas où les preuves sont insuffisantes.
36. ACQUISITION ET VIRALITÉ
Priorité : TikTok, Facebook et partage WhatsApp.
Formats : « Tu reçois ce message, tu fais quoi ? » → analyse SûrCheck → signaux → action recommandée → « Vérifie avant de payer ».
Scénarios de contenu : faux recrutement, faux vendeur, faux concours, faux remboursement, faux service client, faux reçu, phishing.
Utiliser uniquement des cas fictifs ou anonymisés dans les démonstrations.
Commencer organiquement et ne lancer une publicité significative qu’après validation du clic, de l’analyse et du paiement.
37. FUNNEL ET KPI
Suivre : vue vidéo → clic → visite → première analyse → résultat → paiement → deuxième analyse → retour à 7/30 jours.
Mesurer séparément la curiosité et les utilisateurs arrivant juste avant une transaction.
KPIs : analyses/jour, analyses/utilisateur, taux de complétion, temps de réponse, signalements, retour, conversion paiement, revenu par payeur, coût par analyse et faux positifs/négatifs.
Le signal de validation principal est le comportement : l’utilisateur rencontre un doute, utilise SûrCheck, comprend le résultat et accepte éventuellement de payer pour approfondir.
38. VALIDATION TERRAIN
Tester d’abord auprès de 20 à 50 personnes au Bénin.
Collecter des cas anonymisés couvrant les scénarios prioritaires.
Après chaque analyse, demander : « Est-ce que ce résultat vous a aidé ? » et « Auriez-vous payé pour une vérification plus complète ? »
Tester séparément prix, formulation et présentation du paywall.
Corriger chaque semaine à partir des erreurs observées avant d’augmenter fortement l’acquisition.
39. ÉVOLUTION POST-MVP
V1.1 : analyse d’images renforcée, réputation des numéros, partage, packs de crédits.
V1.2 : bibliothèque de scénarios, alertes sur tendances, meilleure détection multilingue et tableau de bord des menaces.
V2 : assistance après incident (« j’ai déjà envoyé l’argent »), checklist de réaction, aide au signalement officiel et mode famille.
V2+ : extension navigateur, partage depuis mobile, intégrations WhatsApp/Instagram et API B2B.
Ne construire les intégrations complexes qu’après validation du cœur produit.
40. PRINCIPES NON NÉGOCIABLES
Ne jamais promettre la sécurité absolue.
Expliquer les résultats importants.
Distinguer risque, preuve et signalement.
Donner une action immédiate.
Minimiser les données.
Modérer les signalements.
Confirmer les paiements côté serveur.
Optimiser le coût par analyse.
Utiliser l’IA comme composant d’un système hybride.
Construire d’abord pour les scénarios béninois et ouest-africains.
